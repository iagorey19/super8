C1. saveData()/persist() sem mutex — corrupção em writes concorrentes [FIXADO]
────────────────────────────────────────────────────────────────────────
  Arquivos: lib/store/core.ts:20-41 + lib/db/index.ts:72-116
  Descrição: Duas chamadas concorrentes a saveData() (ex: updateMatchScore
    + finalizeTournament simultâneos) compartilham a mesma referência _data
    e não têm fila/lock. A segunda chamada pode sobrescrever estado entre
    o cálculo de dirty e o network request da primeira. Dados se intercalam.
  Impacto: Corrupção silenciosa de dados em partidas e resultados.
  Fix: Adicionar promise-chain/mutex no persist(). Ex: encadear Promises
    sequencialmente em vez de executar em paralelo.
  Status: ✅ _persistChain (promise-chain) + flag _persisting em db/index.ts.

C2. Auth registration: falha no Supabase Auth não aborta cadastro [FIXADO]
────────────────────────────────────────────────────────────────────────
  Arquivo: src/app/api/auth/register/route.ts:59-70
  Descrição: Se svc.auth.admin.createUser() falhar (linha 60), o erro é
    apenas logado e a execução continua. O usuário recebe token + cookie
    mesmo sem existir no Supabase Auth. RLS policies e login futuro quebram.
  Impacto: Usuário criado em public.users mas sem registro no Auth.
  Fix: Envolver public.users insert + auth.createUser numa transação.
    Se auth.createUser falhar, fazer rollback do insert e retornar erro 500.
  Status: ✅ auth.admin.createUser() executa ANTES do insert em public.users.

C3. Sync admin deleta registros NÃO INCLUSOS no payload [FIXADO]
────────────────────────────────────────────────────────────────────────
  Arquivo: src/app/api/data/route.ts:291-303
  Descrição: No sync de admin, após upsert, o código SELECT todos os IDs
    existentes e DELETA qualquer um não presente no payload recebido.
    Se o cliente enviar dados incompletos (bug, cache stale, race), a
    deleção é permanente e sem recuperação via este endpoint.
  Impacto: Perda irreversível de dados.
  Fix: (a) Mover para soft-delete (flag active) em vez de DELETE, ou
    (b) Exigir header explícito "confirm-delete: true" para ativar a
    limpeza, ou (c) Remover a lógica de deleção e fazer só upsert.
  Status: ✅ Soft-delete ({ active: false }); pula users, auth, annual_rankings.

C4. Upload: validação de tamanho é no-op [FIXADO]
────────────────────────────────────────────────────────────────────────
  Arquivo: src/app/api/upload/route.ts:38-40
  Descrição: A condição if (type === "fileSize") compara a propriedade
    type do body com a string literal "fileSize". Nenhum cliente jamais
    enviaria type: "fileSize", então o bloco nunca executa. Dentro dele
    o corpo está VAZIO — nenhuma ação de enforcement.
  Impacto: Arquivo de qualquer tamanho passa.
  Fix: Validar content-length REAL antes de criar signed URL, e/ou
    configurar limite no Supabase Storage bucket.
  Status: ✅ Validação real de content-length > MAX_FILE_SIZE retorna 413.

C5. Inscrição em torneio: race condition estoura limite de 8 [FIXADO]
────────────────────────────────────────────────────────────────────────
  Arquivo: src/lib/store/tournaments.ts:640-700 (registerAthleteInTournament)
                e 702-768 (registerMultipleAthletes)
  Descrição: A checagem de duplicata e contagem de vagas (linha 648-650)
    ocorre ANTES do save. Duas requisições simultâneas podem ambas passar
    a checagem e ver existingCount = 7, resultando em 2 registros com
    registration_order = 8 e is_waiting = false — 9 atletas no grupo.
  Impacto: Torneio inicia com mais de 8 atletas por grupo, quebra o
    formato Whist e o chaveamento.
  Fix: (a) Usar upsert com unique constraint na tabela, ou
    (b) Adicionar lock pessimista (SELECT ... FOR UPDATE), ou
    (c) Usar contagem atômica via transação SQL.
  Status: ✅ acquireRegistrationLock() mutex + persist chain.

C6. Senhas em texto puro no seed + troca sem verificar atual [FIXADO]
────────────────────────────────────────────────────────────────────────
  Arquivos: src/lib/seed.ts:19-46 + src/lib/store/users.ts:79-92
  Descrição: Seed contém senhas em plaintext (ex: "admin123",
    "DaniMandeli123"). updateAthlete permite definir nova senha sem
    exigir a senha atual.
  Impacto: (1) Vazamento de credenciais se bundle for inspecionado.
    (2) Qualquer atleta autenticado pode trocar a senha para qualquer
    valor — account takeover.
  Fix Seed: Remover senhas do seed ou usar bcrypt pré-hash.
  Fix updateAthlete: Exigir currentPassword antes de alterar.
  Status: ✅ Senhas removidas do seed. ✅ updateAthlete agora exige
    currentPassword (verifica com bcrypt.compareSync). ✅ UI do perfil
    mostra campo "Senha Atual" condicionalmente ao digitar nova senha.
